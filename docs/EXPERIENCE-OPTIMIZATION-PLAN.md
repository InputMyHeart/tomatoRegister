# 番茄记账：性能与体验优化实施方案

> 方案日期：2026-10-28。本文是实施路线，不代表各项性能问题已经在真实设备上测出。实际优先级以第一阶段的测试环境数据为准。

## 一页概览

| 顺序 | 阶段     | 解决什么问题                             | 完成标志                                 |
| ---- | -------- | ---------------------------------------- | ---------------------------------------- |
| 0    | 固定基线 | 让后续改动能被准确比较和回归             | 测试数据、设备、网络与检查结果记录完整   |
| 1    | 测量     | 找到用户真正等待的环节                   | 有页面和接口的分位耗时、查询次数、失败率 |
| 2    | 分析页   | 降低大范围分析对记录全集与 `skip` 的依赖 | 所有分析模式结果等价，大账本明显改善     |
| 3    | 首页     | 降低首页当月汇总的全量读取成本           | 汇总正确，首屏等待时间改善               |
| 4    | 弱网反馈 | 让写入、同步、导入的状态明确且可恢复     | 无重复写入、假成功或输入丢失             |
| 5    | 发布基线 | 稳定执行检查和手工回归                   | `npm run verify` 通过，测试环境回归完成  |

每一阶段单独实施、验证和提交；阶段 2、3 的先后顺序可在测量后交换。当前项目仍处于开发与测试阶段，生产环境尚未创建，不直接在生产数据上试验。

## 当前代码事实与边界

- [首页接口](../cloudfunctions/tomatoLedger/handlers/dashboard.handler.js)逐页读取当月记录，在云函数内计算汇总；最近 10 条和历史总笔数另行查询。
- [分析接口](../cloudfunctions/tomatoLedger/handlers/analysis.handler.js)每次以 100 条一页读取目标范围，使用 `skip(offset)`；年度、同期对比可能再读取其他范围。
- [明细接口](../cloudfunctions/tomatoLedger/handlers/record.handler.js)已使用游标分页，月度汇总、月笔数和历史笔数由云端返回。不要为了本方案把明细退回到客户端按已加载记录求和。
- [请求入口](../miniprogram/services/api.js)统一调用 `tomatoLedger`；[反馈模块](../miniprogram/services/feedback-ui.js)已提供 Loading、Toast；[页面跳转计时](../miniprogram/utils/navigation-timing.js)已有基础日志。
- 云函数按请求重新读取用户和账本并校验角色。优化只能改变读取和展示方式，不能依赖客户端传来的权限、身份或缓存结论。
- `plan/PENDING.md` 暂缓 CI、监控面板、告警和灰度发布。本方案使用现有日志、测试命令和测试环境，不预设引入这些设施。

## 阶段 0：固定可比较的基线

1. 在 **test** 云环境准备专用测试账本：空账本、少量记录、跨月跨年账本、单月 51 条与 101 条账本，以及一个较大账本。较大账本的具体规模以测试环境可承受范围为准。覆盖收入、支出、分类、共享成员、预算、闰日及同一天多条记录。测试数据只放测试环境，不写入仓库。
2. 固定测试条件：微信开发者工具和至少一台真机、网络条件、登录账号、账本数据量、冷启动或热进入。每组重复多次，记录中位数和较慢的一档耗时；不要只取一次最快值。
3. 先运行 `npm run verify` 并记录现有失败项。目前已观察到格式检查会被多个非本方案文件阻断；先把这一状态记入基线，阶段 5 再集中修复，避免把它误判成查询优化的回归。
4. 记录首页、明细、分析的当前数值和屏幕截图，后续作为结果等价与视觉回归的参照。

**产出：**一张基线表，列出账本规模、设备、网络、页面、耗时、请求次数、云函数错误码及截图位置。测试记录可以放在本地工作记录；不得包含真实用户资料或密钥。

## 阶段 1：测量并决定先优化哪里

### 要测的指标

| 指标                               | 采集点                                    | 用途                                             |
| ---------------------------------- | ----------------------------------------- | ------------------------------------------------ |
| 点击到页面壳层显示                 | 现有 `navigation-timing`                  | 识别导航或页面初始化问题                         |
| 点击到真实内容可见                 | 首页、明细、分析的 Loading → Ready 切换后 | 代表用户实际等待；`onReady` 本身不能代替这个指标 |
| 云函数总耗时、结果与错误码         | `tomatoLedger/index.js` 的结构化日志      | 区分服务端慢、失败和前端渲染慢                   |
| 数据库查询次数、每段耗时、返回行数 | 只在测试环境对热点 handler 增加分段计时   | 找到全量读取、排序、用户信息补全等具体成本       |
| 接口调用次数                       | 前端按 route 统计，或按服务端日志聚合     | 发现切换 Tab、返回页面、同步时的重复请求         |

不记录完整记录内容、昵称、邀请令牌或请求 payload。若需要关联前后端一次请求，可给请求增加不含用户信息的 `requestId`；保持现有 `{ route, payload }` 和 `{ ok, data }` 协议。

### 判定办法

先按用户等待时间和出现频率排序。如果慢在云函数，再看查询段；如果慢在云函数返回之后，再检查页面状态切换、图表绘制和 `setData` 的数据量。只有在同一测试条件下复测出改善，才保留优化。目标值由基线确定；可先把“较慢一档耗时下降至少 20%，结果完全一致”作为候选验收线，而不是当前性能承诺。

**阶段出口：**明确最慢的 1–2 条用户路径、对应的代码和查询段；确认阶段 2、3 的实际实施顺序。

## 阶段 2：分析页查询优化

### 现有成本

`getAnalysisRecords()` 使用 `skip(offset).limit(100)` 收集记录。`month`、`year`、`calendar`、`custom`、`all` 需要的指标和比较范围不同；当前年趋势、上期对比还可能追加查询。记录越多，传入云函数的行数、循环次数和内存计算越多。CloudBase 官方说明大偏移量 `skip` 会逐渐变慢，建议采用游标分页，并核对查询索引。

### 实施顺序

1. **逐项列出输出契约。**从现有返回值和测试梳理概览、上期同期、日/月/年趋势、分类排名、账户、成员、日历及预算。为每项标出所需字段、日期范围、分组粒度和四舍五入规则。保留 `ledger/analysis/get` 路由及前端返回结构。
2. **先做低风险查询改造。**给内部批量读取改为稳定的复合游标，使用与排序一致的 `date`、`createdAt`、`_id` 条件；限定返回字段。查询条件或排序调整后，在 test 环境检查索引命中。内部游标不改变对外 `record/list` 的 `{ date, id }` 契约。
3. **按指标迁移到云端聚合。**优先处理总收入、总支出、笔数、分类与账户合计等可按范围分组的指标；趋势按日期或月份分组。对“最大一笔”“最近 N 条”等保留有界查询。将多个指标能共享的日期范围合并处理，但不要为了减少调用而让单个聚合承担过大的全集排序。
4. **保留兼容的计算出口。**纯计算函数继续负责补零时间桶、展示排序和数值格式；聚合结果先转换成现有数据形状。不要引入客户端记录缓存，也不要先做持久化统计表：后者会增加每次写入、导入、删除及分类迁移的一致性负担。
5. **做结果对照。**使用相同测试账本比较旧实现与新实现，覆盖空账本、仅收入、仅支出、同日多条、月末、闰年、跨年、全部时间、共享成员和分类迁移。金额按现有金额规则逐项比较，不能只比图表是否显示。

如果聚合算子、索引或结果对照不满足要求，先保留低风险的游标与字段裁剪改造，再根据测量决定是否继续聚合。

**阶段出口：**所有模式结果等价；大账本的耗时、读取行数和云函数内存表现优于基线；普通账本没有可感知的回退。

## 阶段 3：首页汇总优化

### 现有成本

`getDashboard()` 会逐页读取当月全部记录，然后计算收支、结余、笔数、最大支出和支出最多分类。最近 10 条与历史总数已经是独立查询，应该继续保持“最近 10 条来自整个账本历史”的语义。

### 实施顺序

1. 先使用阶段 1 的测量确认首页瓶颈是否真的在当月记录读取。若主要耗时在头像补全、云函数冷启动或前端渲染，先处理实际瓶颈。
2. 将当月收入、支出、笔数与最大支出改成范围聚合；支出最多分类按现有 `parentCategory || categoryName || "其他"` 规则聚合。保留零支出时的 `-` 展示语义，不把“其他”当成真实冠军分类。
3. 最近 10 条保持全历史排序与 `limit(10)`；历史总数继续按账本统计。检查这些查询与 [`docs/DATABASE.md`](./DATABASE.md) 所列索引的实际命中情况，需要新索引时先在 test 环境建立并记录变更。
4. 对照现有 `dashboard.helpers.js` 和测试，覆盖 0、1、50、51、100、101 条及跨月记录，验证预算比例、结余、最大支出、分类排名和最近 10 条完全一致。

**阶段出口：**首页真实内容显示时间改善；大月数据无需把整月记录逐页搬进云函数内存；返回字段与页面展示保持一致。

## 阶段 4：弱网与操作反馈

### 用户应看到的状态

| 场景               | 页面反馈                                             | 数据处理                     |
| ------------------ | ---------------------------------------------------- | ---------------------------- |
| 读取中             | 稳定壳层与对应骨架；超过正常等待时间可显示“仍在加载” | 继续等待或允许用户主动重试   |
| 读取失败           | 错误说明和明确重试入口                               | 不把未加载误显示成“暂无数据” |
| 写入中             | 按钮禁用、操作进度可见                               | 阻止重复点击和离开时误判成功 |
| 明确写入失败       | 保留表单内容，显示可理解的错误                       | 用户修正或重试               |
| 请求中断、结果未知 | 提示“结果待确认”，重新读取云端状态                   | 未确认前不自动重发写请求     |
| 写入成功           | 成功反馈，再触发当前页面和账本版本刷新               | 以云端确认结果为准           |

### 实施顺序

1. 盘点记录保存/删除、分类迁移、账本设置、手动同步和批量导入的当前状态与提示，优先处理用户会重复点击或丢失输入的路径。复用 `feedback-ui`、`tl-button`、公共骨架和错误/空态组件，不新建页面私有通用组件。
2. 为读请求分类网络错误、超时、权限变化和业务校验错误；读请求可由用户主动重试。写请求默认不自动重试，因为响应丢失时云端可能已经完成写入。若以后要自动重试写入，需先有服务端幂等键及去重契约。
3. 手动同步维持现有“账号 → 账本 → 当前账本分类全部完成才提示成功”语义；失败时不更新成功时间。共享账本版本变化仍触发当前可见页面重查。
4. 用开发者工具与真机测试慢网、断网、请求超时、返回前切换账号/账本、重复点击、后台再回来。检查服务端最终记录数量和前端提示是否一致。

**阶段出口：**没有“失败却提示成功”、重复写入、输入丢失或 Loading 与 Ready 同时出现；弱网时用户知道下一步能做什么。

## 阶段 5：检查、回归与发布准备

1. 清理当前阻挡 `npm run verify` 的格式问题。只格式化被确认的文件并审查差异，不对有大量在途修改的工作区直接运行全量 `npm run format`。
2. 每个查询阶段增加**结果等价**和**大数据量边界**测试；弱网阶段测试重复提交、旧请求覆盖和结果未知。运行 `npm run verify`。涉及 UI 时额外运行 `npm run ui:check`；关键页面视觉变化运行 `npm run visual:check`。
3. 在 test 环境按 [`docs/REGRESSION.md`](./REGRESSION.md) 完成登录、账本、收支 CRUD、分页筛选、邀请权限、分类迁移、预算，以及两账号共享账本和弱网回归。测试索引变更与云函数一起演练。
4. 记录优化前后相同条件下的耗时、查询量和错误率，附上结果等价测试结论。若改善不明显或引入一致性风险，回退该阶段的实现；不要为了保留复杂代码而降低验收标准。
5. 将最终查询方式、索引和手工回归步骤更新到 `docs/DATABASE.md`、`docs/CACHE-POLICY.md` 与 `docs/REGRESSION.md`。生产环境创建、备份和恢复验证仍按 `plan/PENDING.md` 的条件另行推进。

## 预计改动范围与顺序

| 阶段 | 主要文件或位置                                                                     | 风险与回退重点                                   |
| ---- | ---------------------------------------------------------------------------------- | ------------------------------------------------ |
| 1    | 前端 `services/api.js`、页面状态点；云函数 `index.js`、热点 handler 的测试环境计时 | 日志只记指标，不记用户数据；去掉计时代码即可回退 |
| 2    | `analysis.handler.js`、`analysis.helpers.js`、分析测试、索引文档                   | 分组与金额结果差异；保留旧计算测试作对照         |
| 3    | `dashboard.handler.js`、`dashboard.helpers.js`、首页测试、索引文档                 | 最近 10 条和预算语义变化；逐字段对照旧结果       |
| 4    | 记录/分类/设置页面、`feedback-ui.js`、相关交互测试                                 | 重复写入和结果未知；先保留人工重查路径           |
| 5    | 格式问题文件、回归文档与测试环境配置                                               | 避免一次性格式化覆盖其他在途改动                 |

## 参考依据

- [CloudBase：优化云数据库查询性能](https://docs.cloudbase.net/recipes/optimize-database-query-performance)：定位慢查询、核对组合索引、避免大偏移量 `skip`。
- [CloudBase：聚合查询](https://docs.cloudbase.net/database/aggregate)：按范围尽早过滤、利用索引和聚合算子。
- [CloudBase：索引管理](https://docs.cloudbase.net/database/data-index)：在目标环境核对索引配置与命中情况。

以上官方资料提供优化方向；本项目采用哪种查询与索引，应由 test 环境的真实测量和结果等价测试决定。
